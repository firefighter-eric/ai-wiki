# 文本扩散语言模型

## TL;DR（快速导读）

DiffusionGemma 在一个文本块内多次并行修正，块与块之间仍按顺序生成。收益是特定硬件和请求规模下的延迟折中；输出 token/s、计算量、首字等待和任务质量需要分别比较。

阅读重点：先按问题选择路线，再核对比较条件与证据边界。

## 先用一个问题理解

可以把一段待定答案反复完善，而不是每次只补下一个词。但多轮修正也要计算；看速度时需计算整段生成，不能只看一次并行步骤。

## 主题定义

文本扩散语言模型讨论的是：能否把传统 diffusion model 的“从噪声逐步修正”思想迁移到离散文本生成上，从而替代或补充自回归 LLM 的逐 token decoding。它不是文生图 topic 的子页，也不是一般 diffusion 的概念页；这里的核心问题是**语言序列如何被表示为可并行 denoise 的 canvas，以及这种生成方式在速度、质量、可控性和部署形态上与自回归模型有什么结构性差异**。

在当前知识库中，这一主题的主要入口是 [DiffusionGemma](../concepts/DiffusionGemma.md)。它将 `Gemma 4 26B A4B MoE` 改造成 text diffusion 生成模型，并把输出组织成 `256-token canvas` 的 block-autoregressive denoising。上游背景则来自 `Gemini Diffusion`，它说明 Google DeepMind 已经把 text diffusion 视为探索更高速度、更强 iterative refinement 和编辑能力的方向。

## 核心问题

- 离散 token 如何定义“噪声”：是 masked token、随机 token，还是更复杂的离散状态分布。
- canvas 内的双向 denoising 如何与 canvas 间的自回归拼接结合。
- text diffusion 的速度优势到底来自哪里，为什么它主要出现在低并发、本地单用户场景。
- 这种生成方式是否真的提升了全局约束、编辑、代码填充、结构化任务，还是只改变了推理成本曲线。
- sampler、entropy bound、adaptive stopping 等新参数如何影响质量、速度和稳定性。

## 主线脉络 / 方法分层

- **自回归瓶颈层**：传统 LLM 对单个用户逐 token 生成时，常受 memory bandwidth 限制；云端高并发服务可以通过 batch 提高硬件利用率，但本地单用户无法自然享受这一点。
- **canvas 并行生成层**：DiffusionGemma 将一个 `256-token` canvas 作为生成单位，先随机初始化，再多步并行 denoise。这样每次 forward pass 不再只产出一个 token，而是同时更新整块文本。
- **encoder / denoiser 分工层**：模型用 causal prefill 读入 prompt 并写入 `KV cache`，随后 denoiser 对 canvas 使用 bidirectional attention；这让同一 canvas 内的 token 可以互相看见，从而支持自修正和全局约束传播。
- **block-autoregressive 长输出层**：单个 canvas 仍有限，因此长文本通过“完成一块、提交到 `KV cache`、再生成下一块”的方式扩展；这使文本扩散并未完全抛弃自回归，而是把自回归粒度从 token 提升到 block。
- **部署与硬件层**：DiffusionGemma 的速度收益依赖专用 GPU 的 compute 能力，在 H100、RTX 5090、DGX Spark、DGX Station 等 NVIDIA 栈上被重点优化；在 unified-memory 或高 QPS batch serving 场景中收益可能减弱。

### 延迟由三个阶段组成

[模型卡](../summaries/Google%20DeepMind%20-%202026%20-%20DiffusionGemma%2026B%20A4B%20IT%20Model%20Card.md)与[开发指南](../summaries/Google%20Developers%20-%202026%20-%20DiffusionGemma%20The%20Developer%20Guide.md)描述 prefill、canvas denoising 和块提交。一个 256-token canvas 可以一次修改多个位置，但多个 denoising 步骤仍需重复模型计算；结束一块后再生成下一块，长输出不是整段文本一次完全并行。服务端还要识别流式输出策略：用户何时看到首个可稳定提交文本，不应被总输出 token/s 隐去。

| 指标 | 自回归与扩散对照需要固定什么 |
| --- | --- |
| 质量 | 同任务、提示、模型版本与解码预算 |
| 首个可见结果 | prefill、块提交与流式规则 |
| 总生成时间 | 输出长度、denoising 步数和硬件 |
| 吞吐 | 并发、batch、显存与请求长度分布 |
| 成本 | 总前向计算、能耗和设备利用率 |

[4x 发布说明](../summaries/Google%20-%202026%20-%20DiffusionGemma%204x%20Faster%20Text%20Generation.md)是特定测量条件下的速度主张，不能转写为每个 prompt 都快四倍。[NVIDIA 部署说明](../summaries/NVIDIA%20-%202026%20-%20Run%20DiffusionGemma%20on%20NVIDIA%20for%20Developer-Ready%20High-Throughput%20Text%20Generation.md)强调 GPU 优化；自回归高 batch 也能改善利用率，所以低并发的相对优势不保证在高 QPS 保持。模型卡的任务成绩还显示质量折中，“并行生成”与“更强推理”没有逻辑必然联系。

目前来源有多份文档，但主要来自同一个开发者与部署伙伴，数量不表示多次独立复现。[视觉教程](../summaries/Maarten%20Grootendorst%20-%202026%20-%20A%20Visual%20Guide%20to%20DiffusionGemma.md)帮助解释块内双向关系，是教学归纳，涉及质量与速度时仍回到模型卡和测量说明。Sudoku 展示约束传播的可能性，并不能代表开放域代码、数学或 agent 行为。

与 speculative decoding 相比，扩散改变生成分布与过程；投机解码通常还要验证 draft，二者不能按“同时产多个 token”视为相同。当前库没有足够对应来源进行质量、延迟与成本的统一性能排序。

## 关键争论与分歧

- **速度是否等于更强模型**：当前证据不支持。官方模型卡显示 DiffusionGemma 在多数 benchmark 上低于 `Gemma 4 26B A4B`，因此它是生成范式与延迟曲线的实验，不是质量上限替代。
- **text diffusion 是否适合生产高 QPS 服务**：Google 官方材料提醒，高 QPS 云端服务中自回归模型可以通过 batching 饱和硬件，因此 DiffusionGemma 的优势会下降。当前更稳的结论是它适合低到中等 batch、单加速器、交互式本地工作流。
- **双向 denoising 是否天然更适合结构化问题**：Sudoku 示例支持这个方向，但它仍是高度匹配 diffusion 优势的展示任务。要把该结论推广到代码、数学、规划或 agent workflow，需要更多独立任务证据。
- **DiffusionGemma 是否应归入扩散模型与文生图**：不应直接归入。它借用 diffusion 的 denoising 思想，但任务对象是离散文本生成，主要对照对象是自回归 LLM，而不是 latent diffusion 文生图模型。

### 已验证的系统路线与未披露的训练细节

本页可稳定说明给定公开模型的 canvas、缓存与块生成接口；缺乏完整训练报告时，不补猜训练目标、样本混合或隐含消融。发布文档中的“扩散”是离散文本生成用法，不能把连续图像 diffusion 或 flow matching 的定理无条件搬过来。独立实现、非 NVIDIA 硬件和相同质量预算下的复核仍属开放研究。

## 这里的术语是什么意思

- **token**：词元：模型处理文本的基本单位，可能是一个字、一个词或其片段。
- **KV cache**：键值缓存：保存已经处理过的位置表示，生成新内容时可复用，避免全部重算。
- **prefill**：提示计算阶段：先处理输入提示，再开始逐步生成输出。
- **encoder**：编码器：把输入转成模型内部表示。
